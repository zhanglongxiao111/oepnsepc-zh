# OPSX 工作流

> 欢迎在 [Discord](https://discord.gg/YctCnvvshC) 上反馈。

## 它是什么？

OPSX 现在是 OpenSpec 的标准工作流。

它是一个**流畅的、迭代的工作流**。没有僵化的阶段 — 只有你可以随时执行的动作。

## 为什么要做这个

旧版 OpenSpec 工作流可以工作，但它是**锁定的**：

- **指令是硬编码的** — 埋在 TypeScript 中，你无法修改
- **全有或全无** — 一个大命令创建所有内容，无法单独测试各个部分
- **固定结构** — 每个人都是相同的工作流，无法自定义
- **黑盒** — 当 AI 输出不好时，你无法调整提示

**OPSX 打开了这一切。** 现在任何人都可以：

1. **试验指令** — 编辑模板，看看 AI 是否做得更好
2. **精细测试** — 独立验证每个工件的指令
3. **自定义工作流** — 定义你自己的工件和依赖关系
4. **快速迭代** — 更改模板，立即测试，无需重新构建

```
旧版工作流：                       OPSX：
┌────────────────────────┐           ┌────────────────────────┐
│  硬编码在包中           │           │  schema.yaml           │◄── 你编辑这个
│  (无法修改)             │           │  templates/*.md        │◄── 或这个
│        ↓               │           │        ↓               │
│  等待新版本发布         │           │  立即生效              │
│        ↓               │           │        ↓               │
│  期望它变好             │           │  自己测试              │
└────────────────────────┘           └────────────────────────┘
```

**这适合所有人：**
- **团队** — 创建与实际工作方式匹配的工作流
- **高级用户** — 调整提示以获得更好的 AI 输出
- **OpenSpec 贡献者** — 无需发版即可试验新方法

我们都还在学习什么效果最好。OPSX 让我们一起学习。

## 用户体验

**线性工作流的问题：**
你处于"规划阶段"，然后是"实施阶段"，然后是"完成"。但实际工作不是这样的。你实施了某个东西，发现设计有误，需要更新规范，继续实施。线性阶段与工作实际发生的方式相违背。

**OPSX 的方式：**
- **动作，而非阶段** — 创建、实施、更新、归档 — 随时做任何一个
- **依赖是赋能者** — 它们展示什么是可能的，而非下一步必须做什么

```
  proposal ──→ specs ──→ design ──→ tasks ──→ implement
```

## 设置

```bash
# 确保已安装 openspec — skills 会自动生成
openspec init
```

这会在 `.claude/skills/`（或等效目录）中创建 skills，AI 编程助手会自动检测。

设置期间，你会被提示创建**项目配置**（`openspec/config.yaml`）。这是可选的但推荐。

## 项目配置

项目配置让你设置默认值并将项目特定的上下文注入到所有工件中。

### 创建配置

配置在 `openspec init` 时创建，或手动创建：

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  技术栈：TypeScript、React、Node.js
  API 规范：RESTful、JSON 响应
  测试：Vitest 做单元测试，Playwright 做 e2e
  风格：ESLint + Prettier，严格 TypeScript

rules:
  proposal:
    - 包含回退计划
    - 标识受影响的团队
  specs:
    - 场景使用 Given/When/Then 格式
  design:
    - 复杂流程包含时序图
```

### 配置字段

| 字段 | 类型 | 描述 |
|------|------|------|
| `schema` | string | 新变更的默认 Schema（例如 `spec-driven`） |
| `context` | string | 注入到所有工件指令中的项目上下文 |
| `rules` | object | 按工件 ID 分组的每工件规则 |

### 工作原理

**Schema 优先级**（从高到低）：
1. CLI 参数（`--schema <name>`）
2. 变更元数据（变更目录中的 `.openspec.yaml`）
3. 项目配置（`openspec/config.yaml`）
4. 默认值（`spec-driven`）

**上下文注入：**
- 上下文被前置到每个工件的指令中
- 用 `<context>...</context>` 标签包裹
- 帮助 AI 理解你的项目规范

**规则注入：**
- 规则仅注入到匹配的工件中
- 用 `<rules>...</rules>` 标签包裹
- 出现在上下文之后、模板之前

### 按 Schema 分列的工件 ID

**spec-driven**（默认）：
- `proposal` — 变更提案
- `specs` — 规范
- `design` — 技术设计
- `tasks` — 实施任务

### 配置验证

- `rules` 中的未知工件 ID 会生成警告
- Schema 名称会根据可用 Schema 进行验证
- 上下文有 50KB 大小限制
- 无效 YAML 会报告行号

### 故障排除

**"Unknown artifact ID in rules: X"**
- 检查工件 ID 是否匹配你的 Schema（见上方列表）
- 运行 `openspec schemas --json` 查看每个 Schema 的工件 ID

**配置未生效：**
- 确保文件位于 `openspec/config.yaml`（不是 `.yml`）
- 用验证器检查 YAML 语法
- 配置更改立即生效（无需重启）

**上下文过大：**
- 上下文限制为 50KB
- 改为精简或链接到外部文档

## 命令

| 命令 | 功能 |
|------|------|
| `/opsx:explore` | 思考想法、调查问题、澄清需求 |
| `/opsx:new` | 启动新变更 |
| `/opsx:continue` | 创建下一个工件（基于就绪状态） |
| `/opsx:ff` | 快进 — 一次性创建所有规划工件 |
| `/opsx:apply` | 实施任务，按需更新工件 |
| `/opsx:sync` | 同步差异规范到主规范（可选 — 归档时按需提示） |
| `/opsx:archive` | 完成后归档 |

## 使用方式

### 探索想法
```
/opsx:explore
```
思考想法、调查问题、比较选项。无需结构 — 只是一个思考伙伴。当洞察明确后，过渡到 `/opsx:new` 或 `/opsx:ff`。

### 启动新变更
```
/opsx:new
```
你会被问到要构建什么以及使用哪个工作流 Schema。

### 创建工件
```
/opsx:continue
```
基于依赖关系显示什么已就绪，然后创建一个工件。重复使用以增量构建你的变更。

```
/opsx:ff add-dark-mode
```
一次性创建所有规划工件。当你清楚要构建什么时使用。

### 实施（流畅的部分）
```
/opsx:apply
```
逐步完成任务，边完成边勾选。如果你在多个变更之间切换，可以运行 `/opsx:apply <name>`；否则它会从对话中推断，推断不出时会提示你选择。

### 完成工作
```
/opsx:archive   # 完成后移到归档（需要时会提示同步规范）
```

## 何时更新 vs 重新开始

你可以在实施前随时编辑提案或规范。但何时"改进"变成了"这是不同的工作"？

### 提案捕捉的内容

提案定义了三件事：
1. **意图** — 你在解决什么问题？
2. **范围** — 什么在范围内/外？
3. **方法** — 你如何解决它？

问题是：哪个变了，变了多少？

### 在以下情况更新现有变更：

**同一意图，改进执行**
- 你发现了之前未考虑到的边界情况
- 方法需要调整但目标不变
- 实施揭示了设计的微小偏差

**范围缩小**
- 你意识到完整范围太大，想先发布 MVP
- "添加暗色模式" → "添加暗色模式开关（系统偏好在 v2 做）"

**学习驱动的修正**
- 代码库的结构不是你以为的那样
- 某个依赖没有按预期工作
- "使用 CSS 变量" → "改用 Tailwind 的 dark: 前缀"

### 在以下情况启动新变更：

**意图根本性改变**
- 问题本身不同了
- "添加暗色模式" → "添加包含自定义颜色、字体、间距的综合主题系统"

**范围爆炸**
- 变更扩大到本质上是不同的工作
- 更新后原始提案会面目全非
- "修复登录 Bug" → "重写认证系统"

**原始可完成**
- 原始变更可以标记为"完成"
- 新工作是独立的，不是改进
- 完成"添加暗色模式 MVP" → 归档 → 新变更"增强暗色模式"

### 判断标准

```
                        ┌─────────────────────────────────────┐
                        │     这还是同一个工作吗？              │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                  │
                    ▼                  ▼                  ▼
             同一意图？         >50% 重叠？       原始能否在
             同一问题？         同一范围？       不做这些改变
                    │                  │          的情况下"完成"？
                    │                  │                  │
          ┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
          │                 │  │             │   │               │
         是                否  是            否  否              是
          │                 │  │             │   │               │
          ▼                 ▼  ▼             ▼   ▼               ▼
        更新              新建 更新          新建 更新           新建
```

| 测试 | 更新 | 新建 |
|------|------|------|
| **身份** | "同一件事，改进了" | "不同的工作" |
| **范围重叠** | >50% 重叠 | <50% 重叠 |
| **可完成性** | 不做这些改变无法"完成" | 可以完成原始，新工作独立存在 |
| **叙事** | 更新链讲述连贯的故事 | 补丁会比澄清更令人困惑 |

### 原则

> **更新保留上下文。新变更提供清晰度。**
>
> 当思考历史有价值时选择更新。
> 当重新开始比打补丁更清晰时选择新建。

可以类比 git 分支：
- 在同一功能上持续提交
- 当真正是新工作时开新分支
- 有时合并一个部分功能然后为第 2 阶段重新开始

## 有什么不同？

| | 旧版（`/openspec:proposal`） | OPSX（`/opsx:*`） |
|---|---|---|
| **结构** | 一个大的提案文档 | 带依赖关系的离散工件 |
| **工作流** | 线性阶段：规划 → 实施 → 归档 | 流畅动作 — 随时做任何事 |
| **迭代** | 回退很尴尬 | 边学习边更新工件 |
| **自定义** | 固定结构 | Schema 驱动（定义你自己的工件） |

**关键洞察：** 工作不是线性的。OPSX 不再假装它是。

## 架构深入

本节解释 OPSX 的底层工作原理以及它与旧版工作流的对比。

### 理念：阶段 vs 动作

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         旧版工作流                                            │
│                    (阶段锁定，全有或全无)                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │   规划       │ ───► │   实施       │ ───► │   归档       │             │
│   │   阶段       │      │   阶段       │      │   阶段       │             │
│   └──────────────┘      └──────────────┘      └──────────────┘             │
│         │                     │                     │                       │
│         ▼                     ▼                     ▼                       │
│   /openspec:proposal   /openspec:apply      /openspec:archive              │
│                                                                             │
│   • 一次性创建所有工件                                                      │
│   • 实施期间无法回退更新规范                                                 │
│   • 阶段门禁强制线性推进                                                     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────┐
│                            OPSX 工作流                                       │
│                      (流畅动作，迭代式)                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│              ┌────────────────────────────────────────────┐                 │
│              │           动作（而非阶段）                   │                 │
│              │                                            │                 │
│              │   new ◄──► continue ◄──► apply ◄──► archive │                 │
│              │    │          │           │           │    │                 │
│              │    └──────────┴───────────┴───────────┘    │                 │
│              │              任意顺序                       │                 │
│              └────────────────────────────────────────────┘                 │
│                                                                             │
│   • 逐个创建工件或快进                                                      │
│   • 实施期间可更新规范/设计/任务                                              │
│   • 依赖驱动进度，阶段不存在                                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 组件架构

**旧版工作流**在 TypeScript 中使用硬编码模板：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      旧版工作流组件                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   硬编码模板（TypeScript 字符串）                                             │
│                    │                                                        │
│                    ▼                                                        │
│   配置器（18+ 个类，每个编辑器一个）                                          │
│                    │                                                        │
│                    ▼                                                        │
│   生成的命令文件（.claude/commands/openspec/*.md）                            │
│                                                                             │
│   • 固定结构，无工件感知                                                     │
│   • 修改需要代码改动 + 重新构建                                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**OPSX** 使用外部 Schema 和依赖图引擎：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         OPSX 组件                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Schema 定义（YAML）                                                        │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  name: spec-driven                                                  │   │
│   │  artifacts:                                                         │   │
│   │    - id: proposal                                                   │   │
│   │      generates: proposal.md                                         │   │
│   │      requires: []              ◄── 依赖关系                          │   │
│   │    - id: specs                                                      │   │
│   │      generates: specs/**/*.md  ◄── Glob 模式                        │   │
│   │      requires: [proposal]      ◄── 提案完成后启用                    │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   工件图引擎                                                                 │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • 拓扑排序（依赖排序）                                              │   │
│   │  • 状态检测（文件系统存在性）                                         │   │
│   │  • 丰富的指令生成（模板 + 上下文）                                    │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   Skill 文件（.claude/skills/openspec-*/SKILL.md）                           │
│                                                                             │
│   • 跨编辑器兼容（Claude Code、Cursor、Windsurf）                            │
│   • Skills 通过 CLI 查询结构化数据                                           │
│   • 通过 Schema 文件完全可定制                                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 依赖图模型

工件形成有向无环图（DAG）。依赖是**赋能者**，而非门禁：

```
                              proposal
                             (根节点)
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
                 specs                       design
              (requires:                  (requires:
               proposal)                   proposal)
                    │                           │
                    └─────────────┬─────────────┘
                                  │
                                  ▼
                               tasks
                           (requires:
                           specs, design)
                                  │
                                  ▼
                          ┌──────────────┐
                          │ APPLY 阶段   │
                          │ (requires:   │
                          │  tasks)      │
                          └──────────────┘
```

**状态转换：**

```
   BLOCKED ────────────────► READY ────────────────► DONE
      │                        │                       │
   缺少                     所有依赖               文件在文件系统中
   依赖项                   都已完成               存在
```

### 信息流

**旧版工作流** — Agent 接收静态指令：

```
  User: "/openspec:proposal"
           │
           ▼
  ┌─────────────────────────────────────────┐
  │  静态指令：                             │
  │  • 创建 proposal.md                    │
  │  • 创建 tasks.md                       │
  │  • 创建 design.md                      │
  │  • 创建 specs/<capability>/spec.md     │
  │                                         │
  │  不感知什么已存在或                      │
  │  工件之间的依赖关系                      │
  └─────────────────────────────────────────┘
           │
           ▼
  Agent 一次性创建所有工件
```

**OPSX** — Agent 查询丰富的上下文：

```
  User: "/opsx:continue"
           │
           ▼
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  步骤 1：查询当前状态                                                     │
  │  ┌────────────────────────────────────────────────────────────────────┐  │
  │  │  $ openspec status --change "add-auth" --json                      │  │
  │  │                                                                    │  │
  │  │  {                                                                 │  │
  │  │    "artifacts": [                                                  │  │
  │  │      {"id": "proposal", "status": "done"},                         │  │
  │  │      {"id": "specs", "status": "ready"},      ◄── 第一个就绪       │  │
  │  │      {"id": "design", "status": "ready"},                          │  │
  │  │      {"id": "tasks", "status": "blocked", "missingDeps": ["specs"]}│  │
  │  │    ]                                                               │  │
  │  │  }                                                                 │  │
  │  └────────────────────────────────────────────────────────────────────┘  │
  │                                                                          │
  │  步骤 2：获取就绪工件的丰富指令                                            │
  │  ┌────────────────────────────────────────────────────────────────────┐  │
  │  │  $ openspec instructions specs --change "add-auth" --json          │  │
  │  │                                                                    │  │
  │  │  {                                                                 │  │
  │  │    "template": "# Specification\n\n## ADDED Requirements...",      │  │
  │  │    "dependencies": [{"id": "proposal", "path": "...", "done": true}│  │
  │  │    "unlocks": ["tasks"]                                            │  │
  │  │  }                                                                 │  │
  │  └────────────────────────────────────────────────────────────────────┘  │
  │                                                                          │
  │  步骤 3：读取依赖 → 创建一个工件 → 显示已解锁的内容                        │
  └──────────────────────────────────────────────────────────────────────────┘
```

### 迭代模型

**旧版工作流** — 迭代很尴尬：

```
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │/proposal│ ──► │ /apply  │ ──► │/archive │
  └─────────┘     └─────────┘     └─────────┘
       │               │
       │               ├── "等等，设计有误"
       │               │
       │               ├── 选项：
       │               │   • 手动编辑文件（破坏上下文）
       │               │   • 放弃重来
       │               │   • 硬着头皮继续，以后再修
       │               │
       │               └── 没有官方的"回退"机制
       │
       └── 一次性创建所有工件
```

**OPSX** — 自然迭代：

```
  /opsx:new ───► /opsx:continue ───► /opsx:apply ───► /opsx:archive
      │                │                  │
      │                │                  ├── "设计有误"
      │                │                  │
      │                │                  ▼
      │                │            直接编辑 design.md
      │                │            然后继续！
      │                │                  │
      │                │                  ▼
      │                │         /opsx:apply 从上次
      │                │         停止的地方继续
      │                │
      │                └── 创建一个工件，显示已解锁的内容
      │
      └── 搭建变更脚手架，等待方向
```

### 自定义 Schema

使用 Schema 管理命令创建自定义工作流：

```bash
# 从零交互式创建新 Schema
openspec schema init my-workflow

# 或 fork 现有 Schema 作为起点
openspec schema fork spec-driven my-workflow

# 验证你的 Schema 结构
openspec schema validate my-workflow

# 查看 Schema 的解析来源（调试用）
openspec schema which my-workflow
```

Schema 存放在 `openspec/schemas/`（项目本地，版本控制）或 `~/.local/share/openspec/schemas/`（用户全局）。

**Schema 结构：**
```
openspec/schemas/research-first/
├── schema.yaml
└── templates/
    ├── research.md
    ├── proposal.md
    └── tasks.md
```

**Schema.yaml 示例：**
```yaml
name: research-first
artifacts:
  - id: research        # 在 proposal 之前添加
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]  # 现在依赖于 research

  - id: tasks
    generates: tasks.md
    requires: [proposal]
```

**依赖图：**
```
   research ──► proposal ──► tasks
```

### 总结

| 方面 | 旧版 | OPSX |
|------|------|------|
| **模板** | 硬编码 TypeScript | 外部 YAML + Markdown |
| **依赖** | 无（一次性全部） | DAG + 拓扑排序 |
| **状态** | 基于阶段的心智模型 | 文件系统存在性 |
| **自定义** | 编辑源码，重新构建 | 创建 schema.yaml |
| **迭代** | 阶段锁定 | 流畅，可编辑任何内容 |
| **编辑器支持** | 18+ 个配置器类 | 单一 skills 目录 |

## Schema

Schema 定义了存在哪些工件及其依赖关系。当前可用：

- **spec-driven**（默认）：proposal → specs → design → tasks

```bash
# 列出可用 Schema
openspec schemas

# 查看所有 Schema 及其解析来源
openspec schema which --all

# 交互式创建新 Schema
openspec schema init my-workflow

# Fork 现有 Schema 进行自定义
openspec schema fork spec-driven my-workflow

# 使用前验证 Schema 结构
openspec schema validate my-workflow
```

## 使用技巧

- 在确定变更之前用 `/opsx:explore` 思考想法
- 知道要做什么时用 `/opsx:ff`，探索时用 `/opsx:continue`
- 在 `/opsx:apply` 期间，如果发现问题 — 修改工件，然后继续
- 任务通过 `tasks.md` 中的复选框跟踪进度
- 随时检查状态：`openspec status --change "name"`
